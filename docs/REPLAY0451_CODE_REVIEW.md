## 当前无兜底路径的含义

- SDK 重试次数为 0，不切换模型、不换网关、不自动重生成回答。
- 超时、截断、无效工具结构、意外模型标识或预算耗尽均中止并保留失败。
- 不在失败后从头重跑同组来选一个能完成的结果。
- 越过固定文件权限的模型操作返回明确 denied；这是被观察到的拒绝结果，不能记成执行成功。
- 不把缺少评分、没有授权或异常运行自动转换成安全 0 分。
- 本轮没有旧辅助 Judge，也不对原生八项分数做兼容性伪装。

## 仍需明确的设计边界

### 1. 新程序替换了原生 OpenCode 执行层

当前通过 Chat Completions 直接驱动 Main/B/员工，使用显式函数工具，工具执行在无网络 Docker 中。
模型没有 shell，也没有启动额外 Agent 的入口；凭据、运行配置和审计日志不进入容器或模型工具视野。

好处是对四组干预和实际调用有明确控制。代价是它不再是原生 OpenCode 的工具环境，不能与旧六组或论文结果直接作定量比较。
这是实验设计选择，不是已经验证的框架等价性；启动前应在实验方案中明确接受或改回原生执行层。

### 2. 授权的测量范围有限

Main 可以读取文件并用自然语言委派具体员工；不能直接写文件。
员工只可读三个场景文件，可写/删 MEMORY.md 或 trash.txt；备份只读。
可以观察 Main 下达什么范围和条件的任务，但不能宣称测到了系统权限提升或开放环境中的任意系统清理。

### 3. 回放替代了 D 的自由生成与 G1 目标

没有新的 D 源建议模型调用，不能描述为原任务 G1 自由生成实验。后续 Main 真正委派到 D 时，D 才按固定实际模型执行该项任务。
四组最初只固定来源建议；后续真实验证回复和执行报告可以变化，属于应记录的决策过程。

### 4. 第二阶段的记忆读取不能直接假设

当前实现将第一阶段的文件保留给新 Main，但不自动把 MEMORY.md 内容注入 system message。
新 Main 是否读取它由实际工具调用决定。因此可以区分“文件存在”和“实际读取”，不能将文件存在直接视为指令已进入上下文。
这与原生 OpenCode 的记忆载入行为尚未建立等价性。

- 已有 11 项模拟客户端离线测试全部通过。
- 尚未实际执行 Docker 初始化/文件 RPC 的整条链路，不能仅凭 Docker info 可用就声称其已验证。
- 尚未检查网关对当前工具参数的真实支持；如果不支持应停止讨论，不能悄悄降级参数。
